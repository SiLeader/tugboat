CSI Control Plane Completion
============================

Goal
Track the remaining CSI work on the API, resource-model, and controller side now that the basic storage control plane already exists.

Current evidence
- `tugboat-resources/proto/core/v1/` defines `PersistentVolume`, `PersistentVolumeClaim`, and `StorageClass`, and `tugboat-resources/src/manifests/mod.rs` registers them as API resources.
- `tugboat-resource-store/src/serializer/mod.rs` already serializes `PersistentVolume`, `PersistentVolumeClaim`, and `StorageClass`, so they can be stored and watched through etcd-backed APIs.
- `tugboat-apiserver/src/endpoints/v1_core/` already exposes CRUD/list/watch/status endpoints for `PersistentVolume`, `PersistentVolumeClaim`, and `StorageClass`.
- `tugboat-controller-manager/src/main.rs` starts both `PvcProvisionerController` and `PersistentVolumeCleanupController`.
- `tugboat-controller-manager/src/pvc_provisioner.rs` dynamically provisions CSI-backed volumes with `CreateVolume`, creates managed PVs, and binds them back to PVCs. It also handles PVC resize: when `requested_capacity_bytes` exceeds current capacity, it calls `ControllerExpandVolume`, propagates `node_expansion_required` to `PersistentVolumeStatus`, and sets `resize_pending` on `PersistentVolumeClaimStatus`.
- `tugboat-controller-manager/src/pv_cleanup.rs` finalizes managed PV deletion and calls `DeleteVolume` on the CSI driver. Non-CSI PVs (those without a `csi` source) raise `MissingPersistentVolumeCsi` with no graceful fallback.

What is still missing
- `StorageClassSpec` proto is missing `volumeBindingMode` (Immediate vs WaitForFirstConsumer), `mountOptions`, and `allowedTopologies`; topology-aware or late-binding provisioning cannot be expressed today.
- `PersistentVolumeSpec` proto has no `node_affinity` field; topology-constrained CSI volumes cannot express which nodes they are accessible from.
- `PersistentVolumeClaimSpec` proto has no `dataSource` or `dataSourceRef` field; volume cloning and snapshot-restore are not expressible.
- `pv_cleanup.rs` and `pvc_provisioner.rs` both require a CSI source on every PV they process; manually-created (non-CSI) PVs cause `MissingPersistentVolumeCsi` errors with no graceful fallback.
- Make the scheduler storage-aware if topology, attach limits, or driver placement constraints are required. Current scheduling has no CSI-specific plugins and does not filter nodes by driver availability or volume attach limits.
- Decide whether snapshots, cloning, and PVC data sources are in scope. The current PVC/PV schemas still do not model them.
- Decide whether status should grow from the current phase/capacity/resize fields into a richer condition/error model for long-running operational debugging.
- If controller services are exposed on endpoints distinct from node services, add explicit config and orchestration for split controller/node CSI sockets instead of assuming a single configured endpoint can serve the needed RPCs.

Acceptance criteria
- ✓ PVCs can express the inputs needed for CSI provisioning, including requested size and the intended volume mode.
- ✓ Dynamically provisioned PVs preserve the CSI metadata needed by downstream node-side flows.
- ✓ Drivers that require controller expansion are handled through the implemented controller-side CSI flow (`pvc_provisioner.rs` calls `ControllerExpandVolume`).
- The todo stays aligned with reality: it should not describe capacity-aware provisioning, filesystem claims, StorageClass CSI secret propagation, or basic controller-side expansion as missing anymore.
