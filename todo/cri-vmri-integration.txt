CRI/VMRI Integration and Unified Workload Management
==================================================

Goal
Treat VMs and containers uniformly by supporting CRI and/or a specialized VMRI (VM Runtime Interface).

Current evidence
- `tugboat-agent` focuses on VMs.
- CNI and CSI integration is still custom-built for the VM runtime, but the CNI side now emits
  standard `bridge` / `flannel` conflists and can execute mainstream CNI binaries directly.
- CRI is the standard for K8s container runtimes, enabling reuse of many CNI/CSI implementations.

What to implement
- Define a VMRI (VM Runtime Interface) similar to CRI but tailored for VM-specific operations (e.g., migration).
- Explore implementing a CRI-compatible shim for the VM runtime so the `tugboat-agent` can treat VMs as special "containers" or "pods".
- Refactor `tugboat-agent` to unify the deployment pipeline for both VMs and (future) containers.
- Reuse CRI-based CNI and CSI plugins directly if possible, or provide a translation layer.
- Ensure the agent can handle diverse resource types without a complete rewrite when container support is added.

Implementation surfaces
- `tugboat-agent/src/runtime/`
- `tugboat-vm-runtime-interface/src/`
- `tugboat-agent/src/reconciler/`

Acceptance criteria
- `tugboat-agent` can deploy both VMs and containers through a unified interface.
- VM-specific operations like live migration are still available when using the unified interface.
- CSI and CNI integration is cleaner and leverages standard CRI/OCI concepts.
- (Optional) A functional CRI-compatible endpoint for VM operations.
