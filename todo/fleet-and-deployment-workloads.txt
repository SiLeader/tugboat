Fleet and Deployment Workloads
==============================

Goal
Add the higher-level rollout resource for Tugboat workloads and resolve the current naming ambiguity between Fleet and Deployment before implementing the controller logic.

Current evidence
- README.md maps Kubernetes Deployment to Fleet, but the roadmap also lists both Deployment and Fleet as separate unfinished items.
- No Fleet or Deployment resource exists in tugboat-resources/proto/.
- tugboat-controller-manager contains no rollout controller beyond storage provisioning and cleanup.

Required design decision first
- Decide whether Fleet replaces Deployment, whether Deployment is an alias, or whether both resources will exist with different responsibilities.
- Update README and docs once that decision is made so the public API model is unambiguous.

What to implement
- Define the workload resource spec, including template, replica count, rollout strategy, paused flag, revision history, and status.
- Build the controller on top of ReplicaSet semantics rather than creating Ships directly for every rollout action.
- Implement rolling update behavior, rollback support, and rollout status conditions.
- Track revisions so the controller can distinguish current, updated, and previous templates.
- Add garbage collection for old ReplicaSets and their owned Ships according to a clear retention policy.
- Ensure selector and template validation prevents overlapping or dangerous ownership.

Implementation surfaces
- tugboat-resources/proto/
- tugboat-resources/build.rs
- tugboat-resources/src/manifests/mod.rs
- tugboat-resource-store/src/serializer/mod.rs
- tugboat-apiserver/src/endpoints/
- tugboat-apiserver/src/endpoints/resource_registry.rs
- tugboat-controller-manager/src/
- README.md and docs/README_ja.md

Acceptance criteria
- The repository clearly documents whether Fleet, Deployment, or both are part of the supported API.
- Creating the workload resource produces and manages ReplicaSets instead of directly managing loose Ships.
- Rolling updates create a new revision and drain the old revision according to the selected strategy.
- Rollback and pause behavior are explicit and tested.
- Status reports current, updated, available, and unavailable replica counts plus rollout conditions.
