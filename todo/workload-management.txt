Workload Management: ReplicaSet, Deployment, and Fleet
======================================================

Goal
Implement robust workload controllers (ReplicaSet, Deployment, and Fleet) with support for live migration and shared networking.

Current evidence
- `ReplicaSet` and `Deployment` resource definitions and API endpoints are implemented.
- Protobuf models for `ReplicaSet` and `Deployment` exist in `tugboat-resources`.
- `Fleet` is still planned.
- `tugboat-apiserver` handles CRUD for these resources.
- `tugboat-controller-manager` is currently missing the controllers for these resources.

What to implement
- Implement `ReplicaSet` controller in `tugboat-controller-manager` to maintain the desired number of Ships.
- Implement `Deployment` controller to manage `ReplicaSets` and support rollout strategies (RollingUpdate, Recreate).
- Implement `Fleet` resource and controller to manage multi-component Ship groups sharing a network.
- Controllers should support live migration: when moving a Ship between nodes, trigger migration instead of recreation if possible.
- Ensure `shipTemplate` in these resources correctly maps to `ShipSpec`.

Implementation surfaces
- `tugboat-controller-manager/src/`
- `tugboat-resources/proto/` (for Fleet)
- `tugboat-apiserver/src/endpoints/` (for Fleet)

Acceptance criteria
- ✓ `ReplicaSet` and `Deployment` resources are defined and accessible via API.
- ☐ Creating a `Deployment` manages `ReplicaSets` and eventually `Ships`.
- ☐ A `Fleet` successfully launches multiple types of VMs sharing the same `NetworkClass`.
- ☐ When a `Deployment` or `ReplicaSet` requires a `Ship` to move to another node, it uses live migration.
- ☐ Rolling updates proceed with minimal downtime by coordinating with migration logic.
