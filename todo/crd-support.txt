CRD Support and Dynamic Resource Store
====================================

Goal
Move from static, protobuf-based storage to dynamic, JSON-based storage (similar to etcd in Kubernetes) to support Custom Resource Definitions (CRDs).

Current evidence
- `tugboat-resource-store/src/serializer/mod.rs` hard-codes every serializable resource type using protobuf.
- `tugboat-apiserver` discovery and handlers are built on a static list of resource types.
- The system is currently unable to handle resource types not known at compile time.

What to implement
- Refactor `tugboat-resource-store` to use JSON for persistence, enabling dynamic storage of any resource kind.
- Implement an `Unstructured` (or `RawExtension`) type in `tugboat-resources` to hold arbitrary resource data.
- Introduce a `CustomResourceDefinition` (CRD) resource to manage dynamic resource registration and validation.
- Transition existing core resources (Ship, PVC, etc.) to use this JSON-based dynamic storage path.
- Update `tugboat-apiserver` to build discovery information dynamically from registered CRDs and core resources.
- Support runtime CRUD and watch operations for custom resources.

Implementation surfaces
- `tugboat-resource-store/src/serializer/` (Move to JSON serialization)
- `tugboat-resources/src/` (Add Unstructured/RawExtension types)
- `tugboat-apiserver/src/endpoints/` (Dynamic resource discovery and handlers)
- `tugboat-resources/proto/` (Define CRD spec)

Acceptance criteria
- `tugboat-resource-store` can persist and retrieve resources as JSON strings without a fixed protobuf type.
- Users can register new resource kinds via a CRD without rebuilding any component.
- The `tugboat-apiserver` discovery endpoint includes newly registered custom resources.
- Standard CRUD operations work for both core and custom resources via the same generic handler.
- Schema validation for CRDs is functional (even if minimal initially).
